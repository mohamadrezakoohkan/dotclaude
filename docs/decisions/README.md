# The decision log

Binding decisions for dotclaude. Spec §1 (D1–D14) holds v1's closed loops; this folder holds
everything that changed since, and why. `CLAUDE.md` → *Decision records* is the procedure; this file
is the reader's map.

## What is here

| | |
|---|---|
| `TEMPLATE.md` | Copy it to `NNNN-<kebab-slug>.md`. Fill **every** section |
| `NNNN-*.md` | One record per decision, numbered sequentially, never renumbered |

**The log is append-only.** To reverse a decision, write a new record and mark the old one
`Superseded by NNNN`, leaving its text unchanged. A record is never edited to make it accurate in
hindsight — if it turns out to have been wrong or incomplete, that belongs in the record that says so.

`docs/decisions/` never moves into `.specify/`: that tree is regenerated by overwrite (record
`0014`), and an append-only log cannot survive there.

## Status values

- **Proposed** — under discussion, not yet binding.
- **Accepted** — binding. The Status line records *who* approved it and *how*, so a later session can
  tell a considered decision from an assumed one.
- **Superseded by `NNNN`** — reversed by a later record. Text left as written.

## The record-to-spec audit

`npm test` asserts that **every Accepted record whose "Spec sections to update" directs a change to a
numbered section or D-row cites its own ID inside *every* section it named.** A record whose line
begins "none" is exempt from that — but must then say where the change *did* land (`CLAUDE.md`,
`docs/plans/`, or "working practice"), so "none" is a claim rather than a shrug.

This is the check record `0007` wanted and `0016` made native. `/speckit-analyze` performs an
equivalent check across one post-v1 feature's `spec.md`/`plan.md`/`tasks.md`, but it aborts without a
`specs/###-<slug>/` directory, so it cannot reach a v1 amendment — it supplements the test rather than
replacing it.

**Two records are exempt, deliberately and explicitly** — recorded here because the log is
append-only, so the records themselves cannot carry this note:

| Record | Why it is outside the audit |
|---|---|
| `0001` | Adopted the log itself. Its line names §1 only to say it *stays* the current-state summary — it directs no edit that a citation could evidence |
| `0002` | Entered the build phase. It changed the spec's **title line**, not a numbered section, so there is no section for a citation to live in |

The exemption is an explicit two-element set in `test/run.test.mjs`, and the test asserts its exact
contents. Growing it means editing that test deliberately — never a quiet addition. `0016` is
emphatic on this point: the fix for an awkward record is an exemption or a tighter parse, **not**
relaxing the assertion until it passes.

### Sections a record names only to rule out

Four records name §1 in order to say it is **not** changing:

| | Its own words |
|---|---|
| `0003` | "§1 unaffected — say so explicitly if a D15 row is wanted instead" |
| `0015` | "D10's wording is unchanged but its scope widens in practice" |
| `0017` | "**§1 is unchanged**: D1–D14 are v1's closed loops and this is a post-v1 view feature" |
| `0023` | "**§1 is unchanged**: D1–D14 are v1's closed loops and this is a post-v1 launch-mode feature" |

Those three `record:section` pairs are excluded by name in `test/run.test.mjs`, and the test asserts that
list's exact contents too. A negation parser could infer them, but its failure mode is a false alarm on
the next record that phrases it differently — and a false alarm is what pressures an author into
weakening the assertion instead of fixing the cause.

### Why "every named section" rather than "at least one"

The weaker rule was tried first and **hid a real defect**. `0012` named §1, §5 and §9; it was cited in
§1 and §5, so the audit passed — while its §9 consequence (the Resolution bar stating "installed") had
never been applied to the spec at all, even though `public/app.js` had implemented it. Checking each
named section separately is the difference between catching that and missing it. The §9 edit was
applied when the audit found it.

### What the audit does and does not prove

It proves **attribution**: every section a record claimed to change names that record. It does not
prove the change was *correct* — a record could name §3, add its ID to §3, and change the wrong thing.
Catching that needs judgement, not a test.

The remaining blind spot is "none". Four Accepted records rely on it, so it is load-bearing rather than
rare: a record that changes lasting behaviour but declares "none" is invisible to this audit by
construction. The mitigation is the say-where rule above, not a stronger assertion.

## The bar for a new process test

Six of the tests in `test/run.test.mjs` guard **process** rather than product: the constitution's
non-negotiables, `CLAUDE.md`'s line budget, the `AGENTS.md` symlink, record-to-spec citation,
follow-up ledger coverage, and watched-input completeness. Each is cheap and each has caught something
real — the record-to-spec one found `0012`'s unapplied §9 edit, and the watched-input one generalises a
defect that had already happened twice in the same shape.

That is a good record, and it is exactly why the next one needs a bar. Process tests are easy to write,
never fail once written, and accumulate into a suite that looks thorough while testing nothing a user
would notice.

**Before adding one, it must answer: would this have caught a defect that actually happened?**

- The record-to-spec audit: yes — `0012`'s §9 edit, unapplied for a milestone.
- Watched-input completeness: yes — `0009`'s follow-up, unapplied while `0012`'s identical-shaped one
  was applied.
- The ledger: yes — `0005` was open, conditional, and invisible without reading all 17 records.

A test that can only answer "it would prevent a hypothetical" belongs in a record's prose, not in the
suite. Two further rules learned the hard way, both from tests in this file:

- **Prove it can fail.** Break the thing it guards, watch it fail with a message that names the cause,
  then revert. A governance test nobody has seen fail is decoration.
- **Never assert the absence of open work.** The ledger deliberately permits `open` rows. A test that
  forbids them does not close follow-ups; it teaches people to write `—`.
